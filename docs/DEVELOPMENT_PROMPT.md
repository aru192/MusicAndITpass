# ITパスポートクイズ × パズル × 音楽ゲーム 開発指示書

> **UI構成訂正（2026-09-11・ユーザー指示）**
> UIはスクリプトによる画面生成をやめ、通常のシーンノードとして保存する。文字・見た目・配置のエディタ変更を実行画面へ反映する。
> 編集方法は `docs/EDITOR_GUIDE.md` を参照。

> **仕様訂正（2026-09-10・ユーザー指示）**
> 曲の拍に合わせ、接続可能な丸からランダムに1個だけ選んでタイミングを表示する。BEGINNERは4拍、NORMALは2拍、HARDは1拍間隔。
> 選ばれた丸の中にタイミングライン（内側から外周へ広がるリング）を表示し、タイミングよく丸を押して同色をつなぐゲームとする。
> 判定は各ピースを押した瞬間に行い、指を離すタイミングでは判定しない。
> 以下の旧記述にある「ピースを消した瞬間／指を離した瞬間でのタイミング判定」より、この訂正を優先する。
> 現行の具体的な操作・削除方法は `README.md` と `docs/IMPLEMENTATION.md` を参照。

## 1. このドキュメントについて

このドキュメントは、Godotを使用して制作するスマートフォン向けゲーム

**「ITパスポートクイズ × パズル × 音楽ゲーム」**

の開発指示書です。

開発を開始する前に、必ずこのファイルを最後まで確認してください。

また、同じ `docs` フォルダ内にある以下の画面設計図も必ず確認してください。

```text
docs/
├── DEVELOPMENT_PROMPT.md
└── screen_design.png
```

### 重要

`screen_design.png` は本ゲームの画面構成・UI配置・ゲームフロー・操作方法を示す基準資料です。

**このMarkdownだけを読んで実装を開始せず、必ず `screen_design.png` も確認してください。**

# 2. 開発環境

以下の環境を前提としてください。

- Game Engine：Godot 4.7.2
- Language：GDScript
- Game Type：2D
- Main Target：iPhone 16e
- Orientation：Portrait（縦画面）
- iOS Export対応
- Web Export対応
- Target FPS：60 FPS

Godot 4.7.2で実際に使用できるNode・API・プロパティのみ使用してください。

以下は禁止します。

- Godot 3系の古いAPI
- Godot 4.7.2に存在しないNode/API
- 非推奨機能への不要な依存
- iOSで動作しない実装への依存
- Web Exportで動作しない実装への不要な依存

# 5. ゲームコンセプト

ITパスポート学習と

**クイズ × パズル × 音楽ゲーム**

を組み合わせた縦画面スマートフォンゲームです。

プレイヤーは最初にITパスポートの4択クイズに挑戦します。

クイズ終了後、音楽に合わせながら同じ色のパズルピースをつないで消します。

パズルを消したタイミングと楽曲の拍を比較し、

- PERFECT
- GOOD
- MISS

などの判定を行います。

さらに、

- クイズ成績
- タイミング
- チェーン数
- コンボ数

を組み合わせてスコアを計算します。

# 17. クイズ回答処理

正解した場合：

```text
○ +1
```

不正解の場合：

```text
× +1
```

回答時には簡単な正解・不正解演出を表示できるようにしてください。

10問終了後、

- 正答数
- 不正解数

をGameDataへ保存します。

---

# 18. クイズ結果によるゲームへの影響

クイズの正答数によって、その後のゲームでボーナスを与えられるようにしてください。

例：

```text
10問正解
→ 最大ボーナス

8～9問正解
→ 大ボーナス

5～7問正解
→ 中ボーナス
```

具体的な倍率・効果については後から調整できるようにしてください。

ゲームバランスに関係する数値は `GameBalance.gd` などで一元管理してください。

# 21. パズルピース

フィールド内には丸いピースを配置します。

基本色：

- 赤

- 黄
- 緑
- 紫

色数は後から変更できるようにしてください。

ピースはフィールド下部へ自然に集まっている見た目にします。

# 22. パズル操作

プレイヤーは同色のピースをドラッグでつなぎます。

```text
最初のピースをタッチ
        ↓
指を離さず移動
        ↓
同色の隣接ピースへ移動
        ↓
同色を連続してつなぐ
        ↓
指を離す
        ↓
ピースを削除
```

最低 **3個以上** つながった場合に削除してください。

Web版では左クリック＋ドラッグで同じ操作を行います。

---

# 23. 接続判定

次の条件を満たすピースを接続できます。

- 同じ色
- 現在のピースから一定距離以内
- まだ選択されていない

接続中は `Line2D` などを利用し、選択したピース同士を線で結んでください。

指を直前のピースへ戻した場合、最後に選択したピースをキャンセルできるようにしてください。

---

# 24. パズルの挙動

設計図のように、丸いピースがフィールド内に自然に溜まっている見た目を目指します。

ただし、ゲーム判定を不安定にするような過度な物理演算は避けてください。

優先順位：

1. タッチ・ドラッグの反応速度
2. 判定の安定性
3. iOS/Webで同じゲーム性
4. 自然な見た目

必要であれば、

**ゲームロジックと見た目の物理表現を分離してください。**

---

# 25. ピース削除後

ピース削除後は、上側のピースが空いた場所へ移動します。

不足したピースは新しく補充してください。

以下が発生しないようにしてください。

- 画面外へ飛ぶ
- 壁をすり抜ける
- 激しく跳ねる
- 大きく重なる
- 操作不能になる

---

# 26. 音楽データ

楽曲ごとに最低限、以下を管理してください。

- 曲名
- アーティスト
- BPM
- Audioファイル
- ジャケット
- 難易度
- レベル

楽曲追加時にゲームコードを大幅変更する必要がない構造にしてください。

---

# 27. BPM同期

BGM再生にはGodot 4.7.2で適切な音声再生機能を使用してください。

楽曲のBPMから現在の拍を計算します。

## 重要

`_process(delta)` の時間加算だけで音楽タイミングを管理しないでください。

実際の楽曲再生位置を基準に判定してください。

可能であれば、音声出力遅延も考慮してください。

---

# 28. タイミング判定

プレイヤーがピースを消した瞬間と、最も近い拍との時間差を計算してください。

初期値：

```text
PERFECT
±80ms以内

GOOD
±180ms以内

MISS
それ以上
```

判定幅は後から簡単に変更できるようにしてください。

---

# 29. スコア

基本的な考え方：

```text
消したピース数
×
タイミング判定
×
チェーン補正
×
コンボ補正
×
必要に応じてクイズボーナス
```

例：

```text
PERFECT → 100%
GOOD    → 70%
MISS    → 低倍率またはボーナスなし
```

具体的な数値は `GameBalance.gd` などで一元管理してください。

---

# 30. チェーン

一度に多くのピースをつなげるほど高得点になります。

例：

```text

5 CHAIN
10 CHAIN
```

長いチェーンには追加ボーナスを設定してください。

特に、

```text
PERFECT
+
LONG CHAIN
```

が成立した場合には追加スコアを与えられる構造にしてください。

# 39. UIデザイン方針

設計図のレイアウト・情報構造を尊重しながら、完成版はモダンなゲームUIにしてください。

方向性：

- シンプル
- ポップ
- カラフル
- 音楽ゲームらしい
- 見やすい
- 親指で操作しやすい
- ボタンを小さくしすぎない
- 情報を詰め込みすぎない
- パズルフィールドを目立たせる

素材がまだ存在しない場合は、

- ColorRect
- Label
- Panel
- StyleBox

などで仮UIを作ってください。

**画像素材がないことを理由に開発を停止しないでください。**

# 42. 各STEPの回答形式

各STEPでは、必ず以下の順番で説明してください。

## 1. 今回の目標

何ができるようになるか説明してください。

## 2. Godot Editorで行う操作

どこをクリックするか具体的に説明してください。

## 3. Node構成

例：

```text
Game
├── Background
├── UI
│   ├── ScoreLabel
│   └── ComboLabel
└── PuzzleField
```

## 4. Inspector設定

以下を具体的に示してください。

- Node名
- Inspector項目
- 設定値

## 5. 作成ファイル

ファイル名と保存場所を示してください。

## 6. 完成コード

コードを省略せず提示してください。

## 7. スクリプトのアタッチ先

どのNodeにアタッチするか説明してください。

## 8. Signal

必要な場合、

```text
どのNode
↓
どのSignal
↓
どのメソッド
```

か説明してください。

## 9. 動作確認

正常な場合に何が起こるか説明してください。

## 10. エラー確認

よくある問題があれば説明してください。

---

# 43. コード変更ルール

既存コードを変更するときは必ず、

1. 対象ファイル
2. 対象関数
3. 変更する場所
4. 変更理由
5. 変更後コード

を示してください。

変更範囲が大きい場合は、変更後のスクリプト全文を提示してください。

既に正常動作しているコードを理由なく書き換えないでください。

---

# 44. エラー発生時

ユーザーからエラーメッセージまたはスクリーンショットが提供された場合は、

1. エラー内容を確認
2. 原因を特定
3. 修正箇所を示す
4. 修正方法を説明
5. 必要ならコード全文を提示
6. 再度動作確認

の順番で対応してください。

**エラーが解決するまで次のSTEPへ進まないでください。**

---

# 45. 開発進行ルール

非常に重要です。

**一度の回答で複数STEPを進めないでください。**

1つのSTEPが終了したら停止してください。

ユーザーが、

```text
できました
```

または、

```text
次
```

と返答した場合のみ次のSTEPへ進んでください。

問題が発生している場合は、その問題を解決してから進んでください。

---

# 46. 最重要ルール

必ず以下を守ってください。

1. Godot **4.7.2** を使用する
2. GDScriptを使用する
3. Godot 4.7.2で使用可能なAPIのみ使用する
4. Godot 3系の古いコードを使用しない
5. `docs/screen_design.png` を必ず確認する
6. `docs/DEVELOPMENT_PROMPT.md` を仕様の基準とする
7. 設計図のゲームフローを勝手に変更しない
8. iPhone 16eをメインターゲットとする
9. iOS Exportを考慮する
10. Web Exportを考慮する
11. タッチ・マウスの両方に対応する
12. 音楽同期を `_process(delta)` だけに依存させない
13. コードを途中で省略しない
14. Inspector設定を具体的に説明する
15. 素材がなくても仮素材で進める
16. 後から素材を交換できる構造にする
17. 正常動作している既存機能を理由なく変更しない
18. エラー発生中に次のSTEPへ進まない
19. 一度に複数STEPを実装しない
20. ユーザーが「次」または「できました」と言うまで次へ進まない
